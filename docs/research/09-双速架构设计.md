# 09 · 双速架构设计（LLM 探索教学 + 识图快跑 + LLM 兜底）

> 2026-08-29 ｜ 由用户提议，M2 的目标架构 ｜ 状态：设计稿，待实施

## 0. 动机（用户观察）

M1 实跑显示：流程中 90% 的操作是机械重复的（固定按钮、固定结算流程、固定弹窗处理），大模型每步 3~10 秒的决策时延是主要时间浪费；钱不是问题，速度和确定性才是。

## 1. 核心思想：把"知识卡"升级为"可执行剧本"

M1 的知识卡是人/模型可读的文本。双速架构把它升级为**机器可直接执行的流程剧本**：

```
tasks/
├── daily.yaml                 # 任务清单（不变）
└── flows/
    ├── claim_gifts.yaml       # 剧本：步骤化的可执行流程
    └── anchors/claim_gifts/   # 锚点图：每个需要"找位置"的步骤一张小图
        ├── gift_btn.png       #   （探索时从截图中自动裁剪！）
        └── claim_all.png
```

剧本步骤结构（每步四要素）：

```yaml
- find:  {anchor: gift_btn.png, or: [text: "プレゼント"], fallback_coord: [1210, 560]}
  act:   click
  expect:{change_above: 0.05}        # 点击后画面变化下限（没有就是失败）
  on_fail: ask_llm                    # 卡住时的处理策略
```

- `find` 三级定位：**模板匹配（锚点图）→ 文字（OCR）→ 固定坐标兜底**——比纯 LLM 稳定得多；
- `expect` 让每步自带成功判据，执行器自己知道有没有点中；
- 像素风游戏 + 固定 1280×720 = 模板匹配的理想场景（阈值可开很高，基本零误匹配）。

## 2. 三个角色的分工

### 2.1 Slow path —— LLM 探索者（贵模型，用得少）

触发条件（任一）：
- 任务没有剧本（新任务 / 剧本被标记失效）；
- 执行器上抛异常（连续 N 步 expect 不满足、看门狗触发、403/blocked）。

职责：
1. **探索 + 录制**：像 M1 那样摸流程，但每完成一步，把该步的关键按钮从当前帧**自动裁剪成锚点图**（模板图哪来的问题就此消失——探索的副产品，零人工打标），并记录四要素；
2. 处理现场异常（关弹窗、恢复状态）；
3. 修复剧本：探索结束后把"实际路径"写回剧本（PATCH 而非重写，减少漂移）；
4. 输出知识卡（保留现有机制，作为给下一次探索的提示）。

### 2.2 Fast path —— 识图执行器（无模型，快 10~50 倍）

- 逐步执行剧本：matchTemplate（OpenCV）找锚点 → click → 截图验证 expect → 下一步；
- 每步 0.1~0.3 秒（截图 30ms + 匹配 5ms + 点击 50ms + 验证截图 30ms），一条 20 步流程 < 10 秒跑完；
- 等待类步骤（战斗挂机）仍用帧差 wait_stable，与 M1 相同；
- 每日轮换的动态判断（哪些势力关开放、礼物有没有角标）写成**条件步骤**：识图判断（模板/OCR 一问一答）→ 分支，不需要 LLM。

### 2.3 升降级机制（剧本生命周期）

```
新任务 ──→ LLM 探索+录制 ──→ 剧本 v1（shadow 状态）
                                │  带保险执行：看门狗全开，卡住即 LLM 接管
                                ▼
                          连续 2~3 次全流程成功
                                │
                                ▼
                           转正（trusted）──→ 日常默认走 fast path
                                │
                     游戏更新/模板失配/连续失败
                                ▼
                           降级回 LLM 接管 → 修复 → 重新走保险期
```

## 3. 模型策略（用户提议的"换贵模型"）

同意，且双速后才有资格这么做：fast path 承担 ~90% 步数后，LLM 调用从每天 150+ 次降到 5~20 次。可以：
- **探索/剧本修复**：升级到更强的模型（MiMo-V2.5-Pro、Claude、GPT 旗舰）——一天几次，贵也便宜；
- **简单接管**（关个弹窗、点下确认）：便宜模型甚至免费 Flash 档就够；
- 配置里做成按用途分模型。

## 4. 预期收益

| 指标 | M1（纯 LLM） | 双速后 |
| --- | --- | --- |
| 单步时延 | 3~10 s | 0.1~0.3 s（fast path） |
| 全日常时长 | 30~40 分钟（估算） | 3~8 分钟（大头是战斗等待） |
| LLM 调用/天 | 150+ | 5~20（探索+异常） |
| 确定性 | 依赖模型发挥 | 固定流程 100% 一致 |
| 游戏更新抗性 | 强（天然） | 强（失配自动回炉 LLM） |

## 5. 实施计划（挂到 M2）

1. **flow schema + 执行器**：`flows/*.yaml` + `flow_runner.py`（OpenCV matchTemplate + 现有 device 层，约 200 行）；
2. **探索录制模式**：agent 循环加"录制钩子"——每步成功后让模型顺手给出锚点裁剪框，存图存步骤；
3. **fallback 接线**：执行器失败 → 载入现场（截图+剧本+失败步骤）→ 现有 agent 循环接管 → 产出剧本 PATCH；
4. **先迁移 2 个简单任务**（claim_gifts、claim_missions）作为样板，验证升降级机制，再迁移战斗类；
5. 战斗类剧本的特殊性：出击后就是 wait_stable，天然适合剧本化；势力任务的"哪些关开放"用条件步骤。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 锚点图误匹配（活动横幅轮播等动态区域） | 锚点裁剪只取按钮本体小区域；expect 判据兜底 |
| 剧本漂移（LLM 修坏） | PATCH + git 版本化剧本文件，坏了能回滚；shadow 保险期 |
| 每日布局微变（活动横幅占位） | find 多级定位（锚点→OCR→坐标）本身抗布局小位移 |
| 随机弹窗打断 fast path | 每步 expect 失败 → 上抛 LLM 处理 → 返回断点续跑 |
