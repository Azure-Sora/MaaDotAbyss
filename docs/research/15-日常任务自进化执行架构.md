# 15 · 日常任务自进化执行架构

> 2026-09-01 ｜ 第一阶段已落地：轨迹聚合、受限编译、shadow/trusted/degraded、分层校验

## 1 · 问题

旧执行链有两个结构性浪费：

1. 普通日常成功后只把经验写回知识卡，下一次仍可能让 LLM 逐步看图操作；
2. LLM 已在新鲜截图上 `report done` 后，又让同一个模型复看同一画面做 `verify`，随后还可能再调用一次模型更新知识卡。

目标不是让模型不断生成高权限 Python，而是让它逐步退出稳定区：确定性步骤进入受限、可读、可回退的 flow/routine，模型只接管未知状态与决策点。

## 2 · 已落地闭环

```text
LLM slow path 成功
  -> 自动保存完整动作类型 + 有效点击前帧/坐标/画面变化率
  -> 本地账本聚合同类轨迹（64px 网格吸收落点微抖）
  -> 同一安全轨迹重复成功 2 次
  -> 模型只做一次“最短正确路径”语义挑选
  -> 编译 tasks/flows/<task>.yaml（shadow）
  -> 后续默认 fast path
       -> 连续 3 次“flow 完成 + 独立终态验收通过”：trusted
       -> 任一失败：degraded，立即跳过旧 flow，由 LLM 从完整起点重跑并修复
```

运行证据写入 `.local/evolution.json`，候选程序仍是仓库内可审阅的 YAML 与锚点图。账本使用临时文件 + 原子替换，写入中断不会留下半份 JSON。

## 3 · 安全编译边界

第一阶段只自动编译“完整语义可由 click flow 表达”的任务：

- `click`：可编译；只保留画面变化率不低于 2% 的有效点击；
- `observe` / `report`：只读或完成声明，可从回放程序省略；
- `auto` / `click_path` / `skip` / `wait` / `wait_stable`：暂不可编译，整条轨迹只记账，不生成残缺 flow。

这是刻意的保守边界。尤其是包含 `auto` 的轨迹，如果只抽取前后的普通点击，会把“导航片段”误当成完整任务并制造假成功。专用 Python routine 仍优先于通用 flow，不会被后者覆盖。

flow 失败后同一轮 LLM 是从任务中途恢复，该恢复轨迹也不能覆盖完整候选：本轮只记账；下一次 degraded flow 被跳过，LLM 从任务真实起点完整成功后才允许重编译。

## 4 · 校验分层

| 执行层 | 完成依据 | 是否调用模型复核 |
|---|---|---|
| fast routine | 场景、计数、UI 树、转场/网络红线等程序证据 | 否 |
| flow（shadow） | 每步定位与 expect + 独立终态截图验收 | 是；仅保险期 |
| flow（trusted） | 每步定位与 expect，全流程已有连续成功证据 | 否 |
| LLM（默认） | 当前画面上的 `report done + evidence` | 否；复用本轮证据 |
| LLM（严格） | 独立 `Brain.verify` 再看新鲜截图 | 是 |

高风险任务可在 `tasks/daily.yaml` 显式配置：

```yaml
validation: strict
```

runner 中的正常学习路径不再额外调用 `summarize_knowledge`；稳定经验直接沉淀为可执行 flow。达到重复轨迹门槛的那一次会增加一次 flow 蒸馏调用，之后日常走无模型快路。

## 5 · 当前范围与下一阶段

第一阶段解决的是“纯点击日常整任务晋升”和“尾部重复模型校验”。下一阶段可在不放宽安全边界的前提下扩展：

1. 给受限 DSL 增加 `call_routine`、路径点击、显式等待与确定性终态断言；
2. 把完整轨迹切成多个稳定片段，允许 `program -> decision -> program` 的混合计划；
3. 在 GUI 展示 observing/shadow/trusted/degraded、证据次数、失败原因和一键停用/回退；
4. 用真实日常采集快慢路径耗时、模型调用数与降级率，替换设计估算。
